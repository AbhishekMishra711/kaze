Short answer: ek hi backend (modular monolith), alag-alag frontends
Hackathon jeetne ke liye microservices mat banao. Ek FastAPI backend banao jisme andar clean modules hon, aur uske upar role-wise alag frontend screens.

Microservices kyun nahi?
Double-booking ka problem: PS ka sabse bada test hai “exactly one reservation wins”. Ye ek database transaction ya unique constraint se hota hai. Agar reservation, allocator aur hospital state alag services me hongi, to distributed transactions, sagas aur network failures ka jhanjhat aa jayega. 24 ghante me ye risk bekaar hai.
Time: Har service ka alag Docker, deployment, auth aur debugging lagta hai. Wo time forecaster aur baseline comparison me lagao, kyunki judges wahi dekhte hain.
Replay engine: Tumhe same scenario system aur baseline dono par deterministic chalana hai. Ek process me ye aasan hai, 5 services me mushkil.
Demo risk: Live demo me ek service down ho gayi to poora flow ruk jayega.
Kya karna hai: ek backend, andar alag modules

  app/

      hospital.py        # accept/reject, occupancy update, closure
      admin.py           # replay, metrics, baseline compare

      allocator.py       # batch optimizer + hard constraints

Har module ka ek clear interface rakho, jaise allocator.solve(patients, state). Isse code services jaisa clean rehta hai, par deploy ek hi hota hai.

Frontend kaise alag karo
Ek hi React/Streamlit app me role-based routes: /dispatcher, /hospital, /admin.
Login par role milta hai, aur backend har endpoint par role check karta hai. Sirf UI button chhupana kaafi nahi hai, judges ye check karte hain.
Real-time updates ke liye WebSocket ya simple polling (har 2-3 sec) use karo, taaki hospital ka accept/reject dispatcher ko turant dikhe.
“Ambulance admin” ko alag app mat banao. Dispatcher console hi uska kaam kar deti hai. Chaho to ek chhota optional driver/ambulance view (ETA update, arrived button) add kar do, ye demo me achha lagta hai.
Judges ko architecture kaise dikhao
Ek diagram banao: “Modular monolith, single transactional database, 3 role-based frontends, API-first”. Aur ek line bolo:

“Humne jaanbujhkar monolith choose kiya kyunki reservation ki atomicity sabse critical requirement hai. Modules clean boundaries ke saath hain, to zarurat padne par services me split kiya ja sakta hai.”

Ye line judges ko impress karti hai, kyunki isme engineering ka reason dikhta hai.

Ek optional trick
Agar “services” wala feel dena hai, to ML forecaster ko alag chhoti service bana sakte ho (/predict endpoint, alag process). Ye safe hai kyunki ye stateless hai aur isme locking nahi chahiye. Par agar time kam hai, to isse bhi main backend ke andar rakho.

4. State machines
Incident:

SUBMITTED → AI_DRAFTED → ADMIN_APPROVED → SEARCHING → HELD
 → AMBULANCE_ASSIGNED → EN_ROUTE → ARRIVED → HANDED_OVER

7. Allocator ka core flow (tumhara radius logic)
dispatch(incident):
  radius = 5km
  while radius <= MAX (e.g. 40km):
      hospitals = PostGIS ST_DWithin(incident.geom, hospital.geom, radius) AND status=OPEN
      feasible = filter hospitals jinke paas SAARE needed resources hain
                 AND data fresh (last_reported_at < 15 min)    # stale = unconfirmed
      if feasible: break
      radius += 5km
  if feasible:
      score each: urgency × P(available at ETA) − travel_penalty
      for hospital in ranked:
          try hold_units(hospital, needs)   # transaction, neeche dekho
          if ok: assign_ambulance(); return
  else:
      try_transfer(incident)    # movable resource sharing
      else mark UNSERVED with reason, ESCALATE
Hold karne ka transaction (atomic):

sql
BEGIN;
SELECT id FROM resource_units
 WHERE hospital_id=$1 AND resource_type_id=$2 AND status='FREE'
   AND id NOT IN (SELECT unit_id FROM reservations
                  WHERE status IN ('HELD','CONFIRMED','ARRIVED'))
 ORDER BY id LIMIT $3
 FOR UPDATE SKIP LOCKED;
-- in units ke liye reservations INSERT (hold_expires_at = now()+5min)
COMMIT;
FOR UPDATE SKIP LOCKED ki wajah se do requests ek hi bed ko nahi chhoo paati. Multi-resource request (ICU + ventilator) me sab ya kuch nahi rakho. Ek bhi fail ho to rollback.

Hold expiry: ek cron/worker har 30 sec me HELD reservations jinki hold_expires_at nikal gayi, unhe EXPIRED karta hai aur unit free karta hai.

Movable resource sharing (tumhara idea): jab koi hospital poora match nahi karta, lekin sirf ek is_movable resource (ventilator, oxygen cylinder) kam hai, to dusre hospital se resource_transfers request banao. Transfer approve hone tak wo unit dono jagah reserve na ho (ek hi unit_id, to double-count nahi hoga).

8. Waiting queue (tumhara “do log same request kare” wala case)

Worker har 5-10 sec me queue ke sab incidents ko ek saath (batch) allocator ko deta hai, ek-ek karke nahi.
